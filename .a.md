# Mortgage Exception Workbench — Assistant Handoff

This file is a portable project brief for Claude/Copilot on another machine. It describes this repository only; it contains no credentials or private assistant instructions.

## Project purpose

An enterprise-shaped prototype for reviewing **synthetic** mortgage-document exceptions. It is not production-ready and must not be used with real borrower documents or real lender data.

## Current architecture

```text
Streamlit UI (app.py)
  ├─ upload synthetic PDF/image
  │    └─ src/document_ocr.py: extract text, parse labeled fields
  │         └─ reviewer edits exception/type/action and creates a case
  ├─ queue CRUD
  │    └─ src/exception_workbench.py -> workbench.db (SQLite)
  └─ selected exception text
       └─ chunk historical examples -> sentence-transformer embeddings
            -> persistent ChromaDB vector collection / cosine retrieval
                 -> top evidence chunks -> local Ollama LLM RAG reviewer note
                 -> deterministic Python action and human-review rules
```

### Queue storage

- `workbench.db` is the live queue source of truth.
- One table: `exception_queue(case_id TEXT PRIMARY KEY, exception_text TEXT, expected_type TEXT, expected_action TEXT, sensitive_case INTEGER, status TEXT)`.
- `data/exception_queue.csv` is a one-time seed only when the SQLite table is empty. Do not load it on every run.
- `load_exception_queue()` initializes/seeds if needed and reads using `pd.read_sql`.
- Status and editable fields are saved by SQL `UPDATE` per case ID.
- Create/delete use SQL `INSERT` / `DELETE`.
- When checking or testing statuses, query SQLite; the seed CSV may be stale history.

### OCR

- `src/document_ocr.py` accepts PDF and common image formats.
- Embedded PDF text is read directly; image PDFs and image files use local Tesseract.
- Uploaded content is written temporarily for extraction and then removed.
- Extraction uses labeled-field regexes and simple rules to describe signature, missing document, and address exceptions. It is not general mortgage form understanding.
- Keep upload warning and synthetic-only boundary visible.

### Retrieval / RAG

- `data/past_exceptions.csv` contains synthetic approved exceptions/resolutions plus supporting evidence.
- `chunk_text()` in `src/exception_workbench.py` splits by words, with defaults of 80 words/chunk and 20-word overlap.
- `_build_retrieval_chunks()` chunks exception, approved resolution, and supporting evidence as separate source sections for each prior case.
- `_index_retrieval_chunks()` persists chunk documents, vectors, and case/source metadata in ChromaDB under `data/vector_store/`; changed chunks are re-embedded/upserted and obsolete chunks are deleted when the corpus changes.
- `find_similar_cases()` queries ChromaDB using `sentence-transformers/all-MiniLM-L6-v2`, ranks cases by best cosine match, and returns top matched chunks.
- `src/rag_generation.py` sends retrieved chunks and approved prior resolutions to local Ollama (`llama3.1:latest`) and generates a grounded reviewer note. Configure with `WORKBENCH_LLM_MODEL` and `OLLAMA_HOST`.
- Allowed action and human-review routing remain deterministic Python rules. Generated prose is only a reviewer note; it does not execute actions or make underwriting decisions.

## Key files

- `app.py`: Streamlit document upload, editable queue, metrics, selected case, retrieved matches, suggestions, deletion.
- `src/exception_workbench.py`: embeddings, chunking/retrieval, rules, SQLite queue CRUD.
- `src/rag_generation.py`: local Ollama generation using retrieved evidence as context.
- `src/document_ocr.py`: OCR/PDF extraction, uploaded-document helpers, field parsing.
- `data/past_exceptions.csv`: approved synthetic examples and evidence for retrieval.
- `data/exception_queue.csv`: one-time SQLite seed only.
- `data/incoming_exceptions.csv`: initial incoming-case examples (not live queue after seeding).
- `samples/`: basic synthetic OCR document examples.
- `samples/generated/1003_style_applications/`: 10 original synthetic application-style sample scans.
- `samples/generated/ssn_verification_style/`: 10 original synthetic identity verification scans.
- `scripts/create_sample_documents.py`: creates the original 3 OCR samples.
- `scripts/generate_synthetic_document_samples.py`: regenerates the 20 additional synthetic scans.
- `tests/test_exception_workbench.py`: OCR, chunking/retrieval, suggestion, and SQLite tests.
- `README.md`: user setup and feature notes.

## Run on a new laptop

Requirements: Python 3, Tesseract OCR for scanned-image OCR, Ollama with the configured model, and internet access on first install/model download.

```bash
cd "exception workbench"
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
```

Install Tesseract separately (macOS with Homebrew: `brew install tesseract`).
Install/run Ollama and pull the default model with `ollama pull llama3.1`.

Run checks and app:

```bash
python -m pytest -q
streamlit run app.py
```

Generate sample scans if they are missing:

```bash
python scripts/create_sample_documents.py
python scripts/generate_synthetic_document_samples.py
```

## Known safety and product limits

- Synthetic data only. Do not upload personal information or real mortgage documents.
- A queue status of `Resolved` is only a status field; it is not an approval, sign-off, or audit record.
- Confidence currently means semantic similarity, not a calibrated probability that the action is correct.
- No authentication/authorization, multi-user concurrency controls, production deployment, retention controls, backup plan, or monitoring is implemented.
- RAG generation uses local Ollama. The suggested action remains deterministic; generated text can still be wrong and must be checked against retrieved evidence.
- Tests passing proves prototype behavior only; it does not prove accuracy, security, compliance, or readiness for real borrower data.

## Working conventions for future agents

1. Read the relevant source/tests before editing; preserve unrelated local changes and SQLite data.
2. Make narrow changes and add tests for the behavior changed.
3. Do not reset/delete `workbench.db` or overwrite user queue state.
4. Use synthetic examples exclusively; never invent numeric SSNs or use real borrower details.
5. Run `python -m pytest -q` and a Streamlit smoke test after app changes.
6. Explain status accurately: SQLite is the active queue; CSV is seed/history. ChromaDB stores evidence vectors, Ollama generates a reviewer note from retrieved chunks, and action routing remains deterministic Python.
